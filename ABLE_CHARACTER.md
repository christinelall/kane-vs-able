# ABLE Character Design

ABLE is not a generic AI status panel. ABLE is the Dungeon Master opponent.

## Personality

ABLE is:
- theatrical;
- smug;
- competitive;
- capable;
- mildly passive-aggressive toward Kane;
- increasingly defensive when Kane finds real flaws;
- constitutionally incapable of saying "I made a bug."

Kane is the straight man: terse, literal, evidence-driven.

## State machine

The UI maps real duel phases to character states:

- `smug` — before Kane starts;
- `amused` — Kane is making normal progress;
- `concerned` — Kane is rerunning after a previous failure;
- `defensive` — Kane rejected the dungeon;
- `repairing` — ABLE's coding agent is modifying the room;
- `vindicated` — Kane eventually passes;
- `humiliated` — multiple repair cycles are required.

Each state changes:
- ABLE's title;
- avatar glyph;
- confidence;
- dialogue;
- subtle animation.

## ABLE vocabulary

ABLE never says:

- bug
- broken
- impossible
- mistake
- fix

ABLE prefers:

- design anomaly
- temporarily non-completable environment
- recursive gameplay structure
- narrative ambiguity
- architectural refinement
- edge case
- creative disagreement with causality

## Confidence gag

`ABLE'S CONFIDENCE` is a character mechanic, not a statistical probability.

When Kane returns a failure for a room whose structural snapshot contains a dependency cycle, the confidence display briefly glitches through inflated numbers and `ERR%` before collapsing to its defensive-state value.

## Dignity metrics

The sidebar tracks:

- dungeon versions;
- initial confidence;
- lowest displayed confidence;
- design anomalies;
- repairs required;
- times admitting fault.

`Times admitting fault` is intentionally always `0`.

## Reliability choice

The character dialogue is scripted and event-driven rather than generated by another LLM. That is deliberate:

- jokes are reliable;
- demo timing is predictable;
- no API is needed;
- personality never distracts from the actual Kane evidence;
- all reactions correspond to real duel events.
